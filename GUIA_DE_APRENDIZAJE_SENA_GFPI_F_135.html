Estimado aprendiz, la industria global del software atraviesa la transformación más profunda de las últimas décadas. La emergencia de modelos fundacionales de Inteligencia Artificial Generativa ha redefinido el rol del programador: ya no somos meros transcriptores manuales de sintaxis, sino arquitectos de sistemas, directores de contexto y garantes de la seguridad y calidad del software.

Sin embargo, el uso indiscriminado de la inteligencia artificial sin un marco metodológico riguroso suele conducir al fracaso conocido como "Vibe Coding" o desarrollo por improvisación. Cuando un desarrollador solicita código a una IA sin delimitar el alcance, sin un esquema relacional formal y sin especificar los estados de interfaz, el sistema inevitablemente alucina: inventa datos simulados (mocks en memoria), genera componentes monolíticos inmantenibles (God Files), expone credenciales secretas y degrada su coherencia conceptual (Understanding Rot y Context Rot).

Para formar profesionales con estándares de producción de nivel internacional, esta guía adopta el Marco PIC 2026 (Precision, Isolation & Context Framework) y la Tetralogía Documental Canónica (Plan, PRD, User Flow y TRD), articulando un pipeline tecnológico de cuatro plataformas sinérgicas:

  • Google Gemini (Gemas Especializadas): Mentor socrático para ingeniería de requisitos, modelado relacional y especificaciones técnicas sin alucinaciones.
  • Google Stitch (stitch.withgoogle.com): Prototipado visual con tokens de diseño y especificación contractual de los 4 estados de UI.
  • Supabase PostgreSQL: Backend como Servicio (BaaS) que actúa como Fuente Única de Verdad (SSoT) con RLS al 100%, triggers y UUIDs.
  • Google AI Studio (aistudio.google.com/apps): Compilación fullstack reactiva que traduce los planos en código modular conectado en tiempo real.

A través de esta guía, usted construirá paso a paso una aplicación web completa y profesional para su Proyecto Formativo, erradicando la improvisación y dominando las competencias de ingeniería de software más demandadas en el sector productivo. ¡Bienvenido a la era del Desarrollo Guiado por IA!

3.1.1 Estudio de Caso: "El Espejismo del Prompt Mágico"

Situación Problematizadora:
Un desarrollador junior solicita a un modelo de IA generativa comercial: "Crea una aplicación web moderna para citas médicas con login, doctores y pagos".

El modelo entrega en segundos una pantalla visualmente atractiva en React. Sin embargo, al realizar pruebas de usuario surgen los siguientes fallos críticos:
  • Los datos de citas se almacenan en un arreglo temporal con useState([]). Al recargar la página (F5), todos los datos desaparecen.
  • Cualquier usuario puede ver y modificar las historias clínicas de otros pacientes al carecer de políticas de seguridad en base de datos (RLS inexistente).
  • Al solicitar un ajuste menor en la interfaz, la IA reescribe todo el archivo generando errores de sintaxis y eliminando funcionalidades previamente operativas.
Anti-patrón: Simulación en Memoria vs SSoT
// CÓDIGO DEFECTUOSO GENERADO POR IMPROVISACIÓN:
const [citas, setCitas] = useState([
  { id: 1, doctor: "Dr. Mock", fecha: "Hoy" },
  { id: 2, doctor: "Dra. Fake", fecha: "Mañana" }
]); // ALUCINACIÓN: Datos hardcodeados no persistentes

const agendarCita = (nuevaCita) => {
  // ERROR CRÍTICO: No persiste en PostgreSQL
  setCitas([...citas, nuevaCita]);
  alert("Cita creada con éxito"); 
};
// CONSECUENCIA: Pérdida total de datos en recarga y
// violación flagrante de privacidad entre usuarios.
Fallo Estructural: Ausencia de Fuente Única de Verdad (SSoT), falta de arquitectura relacional y omisión de especificación de requisitos BDD.

3.1.2 Preguntas Orientadoras para la Socialización

De forma individual, responda las siguientes interrogantes en su bitácora técnica para posteriormente debatirlas en plenaria grupal:

  1. ¿Por qué los modelos de lenguaje tienden a generar datos simulados (useState, setTimeout) cuando no se les suministra un esquema SQL formal?
  2. ¿Qué implicaciones legales y éticas tendría desplegar en una clínica real una aplicación que carece de Row Level Security (RLS) en su motor de persistencia?
  3. Si un arquitecto tradicional no inicia una edificación sin planos estructurales, ¿por qué muchos programadores intentan codificar software solicitándole código a la IA sin un Plan, un PRD, un User Flow y un TRD?
Conclusión Pedagógica: La Inteligencia Artificial no reemplaza la disciplina de la ingeniería; por el contrario, amplifica exponencialmente las decisiones arquitectónicas del desarrollador. Una buena especificación documental produce código de nivel empresarial; la ausencia de especificación produce alucinaciones costosas.

3.2.1 Matriz Comparativa de Paradigmas de Desarrollo

Criterio Desarrollo Tradicional Manual Improvisación ("Vibe Coding") Desarrollo Guiado por IA (Marco PIC 2026)
Punto de Partida Requisitos estáticos en cascada o historias de usuario en tableros. Prompts abiertos y vagos en interfaces de chat estándar. Tetralogía Documental Canónica (Plan, PRD, User Flow, TRD).
Velocidad de Iteración Lenta; escritura manual de código boilerplate y configuración. Aparentemente rápida al inicio, colapsa en la integración. Óptima y predecible; código modular compilado en minutos con IA.
Fuente de Verdad (SSoT) Servidor backend / ORM tradicional manual. Inexistente o ambigua; abundancia de datos mockeados. Supabase PostgreSQL: RLS al 100%, triggers y UUIDs nativos.
Consistencia Visual UX Depende de bibliotecas CSS o maquetadores manuales. Interfaces incoherentes sin estados de error ni carga. Google Stitch: Tokens visuales y 4 estados de pantalla obligatorios.
Tolerancia a Errores Alta depuración manual mediante breakpoints y logs. Degradación continua (Context Drift) al corregir bugs. Protocolo de Parches Quirúrgicos y verificación Maker-Checker.

3.3.2 Elaboración Paso a Paso de la Tetralogía Documental Canónica

Documento 1: Plan de Proyecto (01_PLAN_PROYECTO.md)
Es la brújula del desarrollo. Delimita el alcance mínimo viable para que la IA no intente construir funcionalidades accesorias innecesarias.

Estructura Obligatoria:
  • Visión del MVP: Propósito central en una frase.
  • Límites de Alcance (Scope Boundaries):
    • [IN-SCOPE] Autenticación Supabase (Email/Password), CRUD de entidad principal, Dashboard con KPIs en tiempo real y UI en 4 estados.
    • [OUT-OF-SCOPE] Pagos internacionales (Stripe), notificaciones push móviles, analítica con ML predictivo (pospuestos para v2.0).
  • Matriz de Dependencias: DDL SQL y RLS ➔ Auth ➔ Prototipos Stitch ➔ Compilación AI Studio.

Documento 2: PRD con Sintaxis Gherkin BDD (02_PRD_PRODUCTO.md)
El PRD documenta el comportamiento esperado del sistema mediante el lenguaje formal Gherkin (Dado / Cuando / Entonces), eliminando cualquier ambigüedad de interpretación para la IA.

Cada Requerimiento Funcional (RF) debe contar con:
  • Código y Nombre: Ej. RF-02: Agendamiento de Citas
  • Prioridad MoSCoW: Must Have / Should Have.
  • Actor: Rol autorizado para ejecutar la acción.
  • Criterio de Aceptación Gherkin: Escenario de éxito y escenario de excepción o validación de error.
Especificación BDD en Gherkin
#### RF-02: Agendamiento de Cita Médica
- Prioridad: Must Have | Actor: Paciente autenticado

Escenario: Paciente agenda cita con éxito
  DADO que el paciente ha iniciado sesión
  Y selecciona al médico "Dr. Carlos Mendoza"
  Y elige la fecha "2026-10-12" a las "10:00 AM"
  CUANDO hace clic en el botón "Confirmar Cita"
  ENTONCES el sistema inserta la fila en 'appointments'
  Y el campo 'owner_id' toma el valor de auth.uid()
  Y la interfaz emite un Toast verde "Cita agendada"
  Y la tabla de citas se actualiza reactivamente.

Escenario: Conflicto de horario no disponible
  DADO que el horario seleccionado ya se encuentra ocupado
  CUANDO el paciente intenta seleccionarlo
  ENTONCES el bloque se muestra deshabilitado en gris
  Y el sistema bloquea el botón de confirmación.
Documento 3: User Flows, Catálogo de Pantallas & 4 Estados de UI (03_USER_FLOWS_UX.md)
El User Flow traza la navegación contractual del sistema. Para erradicar el "Efecto Monovista", el aprendiz debe definir obligatoriamente un Catálogo de Pantallas (Screen Inventory) con mínimo 5 a 8 vistas independientes:
  • SCR-01: Auth & Onboarding (Login / Registro / Recuperación).
  • SCR-02: Dashboard Principal (4 KPIs en vivo + resumen).
  • SCR-03: Explorador de Registros (Tabla + selector Kanban).
  • SCR-04: Detalle 360 del Registro (Ficha técnica profunda).
  • SCR-05: Formulario de Creación (Wizard modular).
  • SCR-06: Configuración & Perfil de Usuario.
Para cada pantalla se especifican contractualmente sus 4 estados:
  1. 1. Empty State: Consulta retorna 0 filas. Ilustración amigable + CTA.
  2. 2. Skeleton Screen: Réplica pulsante animada mientras carga Supabase.
  3. 3. Toast Feedback: Notificación flotante accesible de confirmación.
  4. 4. Error & Retry: Manejo de excepciones (red/RLS) con botón reintentar.

Documento 4: TRD y Arquitectura Técnica (04_TRD_ARQUITECTURA_TECNICA.md)
El TRD fija los contratos técnicos invariantes para evitar que la IA utilice versiones obsoletas o paquetes incompatibles:

  • Stack Frontend: React 19 SPA, Tailwind CSS v3.4+, Lucide React Icons, cliente @supabase/supabase-js v2.x.
  • Arquitectura de Directorios: Modular basada en características (Feature-Driven), separando servicios (services/), contexto (context/), componentes UI base (components/ui/) y componentes de dominio (components/features/).
  • Límite de Contexto: Ningún componente puede superar las 250 líneas de código para evitar Context Rot.
Estructura Modular Estandarizada
src/
├── lib/
│   └── supabaseClient.js      # Singleton con persistencia
├── context/
│   └── AuthContext.jsx        # Provider y hook useAuth()
├── services/
│   ├── profileService.js      # Consultas a public.profiles
│   └── appointmentService.js  # CRUD sobre appointments
├── components/
│   ├── layout/                # Sidebar, Header, KPI Cards
│   ├── ui/                    # Skeletons, Toasts, Modales
│   └── features/              # Tablas de datos, Formularios
├── types/                     # Definición de tipos y esquemas
└── App.jsx                    # Enrutamiento condicional
Tip de Arquitectura: Al modularizar el código en archivos de menos de 250 líneas, la IA puede realizar modificaciones incrementales mediante parches precisos sin alterar ni romper el resto del sistema.

3.3.3 Prototipado Visual Multi-Pantalla con Google Stitch

Paso 1: Generación con Gema 3 y Protocolo Multi-Pantalla en Stitch:
El aprendiz selecciona su estilo visual en el Catálogo de 40 Estilos Frontend (ej. #13 Bento Grid o #2 Glassmorphism) y solicita a la Gema 3 generar el archivo canónico 06_PROMPTS_GOOGLE_STITCH.md alimentándola con el Plan, PRD y User Flow.
Posteriormente, ingresa a stitch.withgoogle.com. Como Google Stitch genera una sola pantalla por prompt, para erradicar el "Efecto Monovista" se construye la Suite Multi-Pantalla dentro del mismo proyecto:
  1. Pantalla 1 (Auth): Pegar Prompt 1 de Login/Registro.
  2. Botón '+ Add Screen': En Stitch, hacer clic en '+ Add Screen' para crear la siguiente vista independiente.
  3. Pantalla 2 (Dashboard): Pegar Prompt 2 (KPIs y widgets).
  4. Pantalla 3 (Explorador): Clic '+ Add Screen' y pegar Prompt 3 (Tabla interactiva de citas).
  5. Pantalla 4 (Detalle 360): Clic '+ Add Screen' y pegar Prompt 4 (Expediente clínico profundo).
  6. Pantalla 5 (Wizard): Clic '+ Add Screen' y pegar Prompt 5 (Formulario de agendamiento por pasos).
  7. Pantalla 6 (Configuración): Clic '+ Add Screen' y pegar Prompt 6 (Ajustes del perfil y clínica).
  8. Consistencia Visual: Reutilizar el mismo estilo del catálogo de 40 estilos y los mismos códigos HEX en todas las vistas.

Trigger de Sincronización Automática de Perfiles
-- 1. Función para actualizar fecha de modificación
CREATE OR REPLACE FUNCTION handle_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 2. Función Trigger: Sincronizar auth.users -> public.profiles
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO public.profiles (id, full_name, email, role)
  VALUES (
    NEW.id,
    COALESCE(NEW.raw_user_meta_data->>'full_name', 'Usuario'),
    NEW.email,
    COALESCE(NEW.raw_user_meta_data->>'role', 'user')
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
Paso 2: Tablas Relacionales y Disparador de Usuarios:
Se crea la tabla public.profiles vinculada a auth.users con eliminación en cascada, y se adjunta el trigger AFTER INSERT ON auth.users.

Posteriormente se crean las tablas del dominio (ej. appointments) asignando llaves UUID generadas por gen_random_uuid() y vinculando el propietario con owner_id UUID REFERENCES public.profiles(id).
DDL de Tablas Principales
-- 3. Tabla de Perfiles de Usuario
CREATE TABLE public.profiles (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  full_name VARCHAR(150) NOT NULL,
  email VARCHAR(150) NOT NULL,
  role VARCHAR(30) DEFAULT 'patient' CHECK (role IN ('doctor', 'patient', 'admin')),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();

-- 4. Tabla de Dominio (Citas Médicas)
CREATE TABLE public.appointments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id UUID NOT NULL REFERENCES public.profiles(id) ON DELETE CASCADE,
  doctor_name VARCHAR(100) NOT NULL,
  patient_name VARCHAR(100) NOT NULL,
  scheduled_at TIMESTAMPTZ NOT NULL,
  status VARCHAR(20) DEFAULT 'pending' CHECK (status IN ('pending', 'confirmed', 'completed', 'canceled')),
  notes TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
Regla Inviolable de Base de Datos: Toda tabla debe utilizar llaves primarias de tipo UUID con gen_random_uuid() para impedir ataques de enumeración secuencial en la API pública.
Paso 3: Activación Obligatoria de Row Level Security (RLS) al 100%:
En Supabase, exponer una tabla sin RLS permite que cualquier persona con la anon key acceda o elimine datos ajenos.

Procedimiento Inviolable:
  1. Habilitar RLS en cada tabla pública mediante ALTER TABLE [tabla] ENABLE ROW LEVEL SECURITY;
  2. Crear políticas granulares e independientes para las 4 operaciones del CRUD (SELECT, INSERT, UPDATE, DELETE).
  3. Garantizar que en la inserción se asigne auth.uid() al owner_id y en la lectura/modificación se valide estrictamente USING (auth.uid() = owner_id).
Script SQL de Políticas RLS Granulares
-- HABILITACIÓN ESTRICTA DE RLS
ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.appointments ENABLE ROW LEVEL SECURITY;

-- POLÍTICAS PARA PROFILES
CREATE POLICY "Permitir lectura de perfiles autenticados"
  ON public.profiles FOR SELECT
  TO authenticated USING (true);

CREATE POLICY "Los usuarios solo editan su propio perfil"
  ON public.profiles FOR UPDATE
  TO authenticated USING (auth.uid() = id);

-- POLÍTICAS PARA APPOINTMENTS (SSoT Y AISLAMIENTO)
CREATE POLICY "Usuarios leen solo sus citas propias"
  ON public.appointments FOR SELECT
  TO authenticated USING (auth.uid() = owner_id);

CREATE POLICY "Usuarios insertan citas vinculadas a su UID"
  ON public.appointments FOR INSERT
  TO authenticated WITH CHECK (auth.uid() = owner_id);

CREATE POLICY "Usuarios actualizan únicamente sus citas"
  ON public.appointments FOR UPDATE
  TO authenticated USING (auth.uid() = owner_id);

CREATE POLICY "Usuarios eliminan únicamente sus citas"
  ON public.appointments FOR DELETE
  TO authenticated USING (auth.uid() = owner_id);

Paso 2: Implementación del Contexto de Autenticación:
El archivo src/context/AuthContext.jsx debe proveer el estado de la sesión, el usuario autenticado y escuchar activamente los cambios de estado mediante supabase.auth.onAuthStateChange.

De esta manera, cuando el usuario inicia sesión o cierra sesión, toda la aplicación reacciona de forma automática protegiendo las vistas privadas.
src/context/AuthContext.jsx
import React, { createContext, useContext, useEffect, useState } from 'react';
import { supabase } from '../lib/supabaseClient';

const AuthContext = createContext({});

export const AuthProvider = ({ children }) => {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    supabase.auth.getSession().then(({ data: { session } }) => {
      setUser(session?.user ?? null);
      setLoading(false);
    });

    const { data: { subscription } } = supabase.auth.onAuthStateChange((_event, session) => {
      setUser(session?.user ?? null);
      setLoading(false);
    });

    return () => subscription.unsubscribe();
  }, []);

  return (
    <AuthContext.Provider value={{ user, loading }}>
      {!loading && children}
    </AuthContext.Provider>
  );
};
export const useAuth = () => useContext(AuthContext);

src/services/appointmentService.js
import { supabase } from '../lib/supabaseClient';

export const appointmentService = {
  async getAll() {
    const { data, error } = await supabase
      .from('appointments')
      .select('*')
      .order('scheduled_at', { ascending: true });
    if (error) throw error;
    return data;
  },

  async create(appointmentData, userId) {
    const { data, error } = await supabase
      .from('appointments')
      .insert([{ ...appointmentData, owner_id: userId }])
      .select()
      .single();
    if (error) throw error;
    return data;
  },

  async delete(appointmentId) {
    const { error } = await supabase
      .from('appointments')
      .delete()
      .eq('id', appointmentId);
    if (error) throw error;
  }
};

5. GLOSARIO DE TÉRMINOS

• BaaS (Backend as a Service): Modelo en la nube para infraestructura, base de datos, autenticación y storage vía APIs unificadas (ej. Supabase).

• BDD (Behavior-Driven Development): Metodología ágil que define el comportamiento del sistema mediante escenarios de negocio Dado / Cuando / Entonces.

• Context Rot: Fenómeno donde el LLM pierde coherencia o alucina código debido a la saturación de su ventana de contexto.

• Gherkin: Lenguaje formal estructurado legible por humanos y máquinas para pruebas de aceptación (GIVEN, WHEN, THEN).

• Google AI Studio Apps: Entorno para compilar y ejecutar prototipos fullstack asistidos por Gemini con previsualización reactiva en vivo.

• Google Stitch: Herramienta para traducir requisitos y prompts en interfaces web de alta fidelidad con tokens de diseño.

• JWT (JSON Web Token): Estándar abierto (RFC 7519) para transmitir identidad y autorización cifrada y firmada digitalmente.

• Maker-Checker: Procedimiento donde un desarrollador construye ("Maker") y un auditor independiente ("Checker") verifica el apego a estándares.

• Marco PIC 2026: Metodología de desarrollo guiado por IA basada en Precision, Isolation y Context.

• RLS (Row Level Security): Seguridad en PostgreSQL que restringe filas accesibles según el identificador criptográfico del usuario (auth.uid()).

• Skeleton Screen: Patrón visual con animación de pulso que imita la estructura de datos mientras se resuelven promesas de red.

• SSoT (Single Source of Truth): Principio donde cada dato reside en una única ubicación autoritativa (PostgreSQL), prohibiendo mocks en frontend.

• Tetralogía Canónica: Conjunto de 4 planos previos al código: 01 Plan de Proyecto, 02 PRD, 03 User Flow y 04 TRD.

• UUID (Universally Unique Identifier): Identificador de 128 bits único a nivel global, utilizado como PK para evitar ataques de enumeración.
